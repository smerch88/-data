# Project guide for Claude Code

This repo is a small system: **Postgres in Docker** + **Node.js/TypeScript backend** for API access + **pgAdmin** for browser-side data editing. Development is driven through slash commands and subagents — do NOT edit files ad hoc; route every change through the matching command.

## ⚠️ READ FIRST, EVERY SESSION

Always read these two files at the start of a session, before proposing solutions:

1. **[docs/CLAUDE_NOTES.md](docs/CLAUDE_NOTES.md)** — cross-session memory: rejected approaches, confirmed user preferences, environment gotchas. When the user rejects your proposal or accepts a non-standard choice, **append an entry there** (or use `/note <text>`). This is not optional — without it, the next session repeats the same mistake. Write entries in English.
2. **[docs/PROJECT_VISION.md](docs/PROJECT_VISION.md)** — product/technical foundation: **EdTech Retention Platform** (churn prediction + LLM explanations + action layer for online schools). Concept, competitive differentiation, architecture, risks, hackathon MVP scope, roadmap.

This file (`CLAUDE.md`) describes only the technical skeleton; `PROJECT_VISION.md` says what we are building on top of it; `CLAUDE_NOTES.md` carries the live state of decisions and gotchas.

**Each subagent has the same instruction in its system prompt** — read `CLAUDE_NOTES.md` before working and append to it after the user corrects them. All entries to `CLAUDE_NOTES.md` are in English regardless of the language the user wrote in.

## Architecture

```
docker-compose.yml          ← postgres + pgadmin
infra/pgadmin/servers.json  ← pgAdmin auto-connects to the postgres container
backend/
  src/index.ts              ← express bootstrap
  src/db.ts                 ← single Knex instance (the only one)
  src/routes/<resource>.ts  ← each resource is its own Router
  knexfile.ts               ← Knex config (reads DATABASE_URL from .env)
  migrations/<ts>_<name>.ts ← Knex migrations
  seeds/<name>.ts           ← Knex seeds
.claude/
  agents/                   ← 4 subagents
  commands/                 ← slash commands
```

## How to run

First time: `/setup` (copies `.env`, installs deps, brings up docker, runs migrations).

Daily:
- `/db-up` — start the containers
- `/api-dev` — start the backend in the background (port 3000)
- pgAdmin: http://localhost:5050

## Workflow for DB changes

1. **Design** — `/schema <entity description>` → the `schema-designer` agent produces a DDL plan. No files are written.
2. **User approves the plan.**
3. **Migration** — `/migrate-new <short description>` → the `db-migrator` agent creates a file in `backend/migrations/`, fills in `up`/`down`, runs typecheck. The migration is NOT applied.
4. **Apply** — `/migrate-up`. Separate step so the user sees exactly what will run.
5. **Data** — `/seed-new <description>` to create a seed file; `/seed` to run all seeds.

This split is intentional: design ≠ writing ≠ applying. Don't collapse the steps into a single agent call.

## Workflow for API

- `/route <method and path, what it accepts and returns>` → `api-builder` creates/edits a file in `backend/src/routes/`, mounts it in `index.ts`.
- If the route requires a new table or column, the agent stops and asks the user to run schema design first.

## Read-only DB queries

`/inspect <question>` → `db-inspector`. It has access to `psql` via `docker compose exec` and only runs SELECT / EXPLAIN / introspection. Any mutation is refused — the user is redirected to `/migrate-new`.

## Remote VPS operations

`/vps <task>` → `vps-operator` runs commands on the production VPS over SSH (key auth via `~/.ssh/data_vps_id_ed25519`, generated by `/vps-bootstrap`). Connection details live in `.env` (`VPS_HOST`, `VPS_USER`, `VPS_PORT`, `VPS_PASSWORD`). The wrapper `bash infra/vps/vps-run.sh "<cmd>"` is the single entry point — never call `ssh` directly from agents.

This is `root@` access, so `vps-operator` confirms before destructive actions and never dumps secret-bearing files into chat. Logs of state-changing sessions go to `infra/vps/logs/` (gitignored).

## Conventions

- TypeScript strict, CommonJS (via tsx in dev). No ESM `"type": "module"` — this is intentional, because Knex CLI with ESM TS is unstable on Windows.
- snake_case in the DB, camelCase in JS. If a mapping is needed, do it explicitly in the route, not globally.
- `created_at` / `updated_at` are `TIMESTAMPTZ`, default `now()`.
- Money is `NUMERIC`, never `FLOAT`.
- Foreign keys ALWAYS specify an explicit `ON DELETE` action.
- No `CREATE TYPE ... AS ENUM` — use a CHECK constraint or a lookup table.

## Don'ts

- Do not edit a migration that has already been applied — create a follow-up.
- Do not create a second Knex instance. Always import `db` from `src/db.ts`.
- Do not concatenate user input into SQL strings — use the query builder or `db.raw('... ?', [val])`.
- Do not add auth, rate-limiting, loggers, or an observability stack to the backend without an explicit ask — this is intentionally a small system.
- Do not commit `.env` (only `.env.example`).
